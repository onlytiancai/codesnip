# 对照实验：如果作用域用固定数组会怎样？

第 5 步引入作用域的时候，我们把 `Env` 的变量表写成了**按需增长的动态数组**：

```c
struct Env {
    Var   *vars;        /* 变量表，按需增长 */
    int    count;
    int    cap;
    struct Env *parent;
};
```

当时只是"顺手这么写了"，其实并没有非这么写不可的理由。
这个目录就是来补上那个理由的。

## 跑一遍

```bash
cd 011/experiments/fixed_env
./run.sh
```

输出（本机 macOS 实测）：

```
递归深度 5     固定数组：正常，输出 5             动态数组：正常，输出 5
递归深度 8     固定数组：💥 段错误（exit 139，栈溢出）  动态数组：正常，输出 8
递归深度 10    固定数组：💥 段错误（exit 139，栈溢出）  动态数组：正常，输出 10
递归深度 20    固定数组：💥 段错误（exit 139，栈溢出）  动态数组：正常，输出 20
递归深度 100   固定数组：💥 段错误（exit 139，栈溢出）  动态数组：正常，输出 100
```

## 为什么

`Env` 是**C 栈上的局部变量**：

```c
case N_CALL: {
    Env local;            /* ← 这里，压在栈上 */
    env_init(&local, e);
    ...
    Flow flow = exec(d->a, &local);   /* ← 函数体又是一个代码块，又压一个 Env */
```

- 固定数组版：`sizeof(Env)` = `2048 × sizeof(Var)` + 指针 ≈ **272 KB**。
  每递归一层要压**两个** `Env`（调用处一个 + 函数体的代码块一个），
  也就是约 **545 KB/层**。macOS 的默认栈是 8 MB，
  所以大约递归到第 **8 层**就爆栈了——`exit 139` 就是 SIGSEGV。
- 动态数组版：`sizeof(Env)` 只有 **24 字节**（一个指针 + 两个 int + 一个指针）。
  栈上放多少层都无所谓，变量本身在堆上。

顺带一提：`MAX_CALL_DEPTH = 128` 这个保护在固定数组版里**根本用不上**——
程序在到达 128 层之前就已经段错误了。

## 这个实验改了哪些地方

`fixed_env/minilang.c` 是 `../../minilang.c` 的一份**改动过的副本**，
只改了 `Env` 这一个结构体和 `env_push` / `env_free` 两个函数：

| | 教程正文（动态数组） | 对照实验（固定数组） |
| --- | --- | --- |
| 结构体 | `Var *vars;` | `Var vars[2048];` |
| `env_push` | `realloc` 按需扩容 | 直接往数组里写 |
| `env_free` | `free(e->vars)` | 什么都不用做 |

其余代码一个字没动，所以两次运行的差别**只可能来自这一个改动**。

## 想自己动手试试

1. 把 `fixed_env/minilang.c` 里的 `2048` 改成 `64`，再跑 `./run.sh`——
   栈溢出发生的深度会变浅（因为每个 `Env` 变小了）。
2. 把 `MAX_NAME` 从 128 改成 16，`sizeof(Var)` 从 136 变成 24，
   `sizeof(Env)` 降到约 50 KB，段错误的深度就会明显变深。
3. 把 `env_push` 里的扩容步长从 `× 2` 改成 `× 8`，看看变量多的时候内存占用有什么变化。
