## 4. 前置知识回顾

上一步我们已经把**求值器**（`eval`）搭起来了，能算 `+ - * / %`。本步全部要用上的是这三样：

**（1）完整的优先级链，第 2 步就建好了。** 语法分析器里有一串函数：
`expression → logical_or → logical_and → equal → compare → add → mul → unary → primary`。
每一层用一个 `bin_level()` 把同优先级的运算符串成**左结合**的循环。

```
        expression()
             │
       logical_or()   ← ||
             │
      logical_and()   ← &&
             │
         equal()      ← == !=
             │
        compare()      ← < <= > >=
             │
          add()        ← + -
             │
          mul()        ← * / %
             │
         unary()       ← - + !
             │
        primary()      ← 数字 / 字符串 / 变量 / 函数调用 / (表达式)
```

**关键：这条链上已经有 `equal` 和 `compare` 了。** 第 2 步做语法分析的时候，`1 < 2` 就能被解析成一棵 `二元 LT` 的树了——只是第 3 步的 `eval` 遇到 `LT` 会直接报错："比较与逻辑运算会在下一步支持"。所以本步**不需要碰语法分析器一行**。

**（2）`eval` 的递归结构和语法分析器正好相反。** 语法分析是"从左到右展开"，求值是"从叶子往回算"。`eval` 里的 `case N_BINARY:` 做三件事：

```c
case N_BINARY: {
    Value x = eval(n->a, e);      /* 左边 */
    Value y = eval(n->b, e);      /* 右边 */
    switch (n->op) { /* 按运算符分派 */ }
}
```

**（3）`Value` 只有数字这一种实数类型。** 第 3 步定型的 `Value { double value; int is_string; char string[]; }` 里，`is_string` 和 `string` 是**提前留好**的（INV-2），第 9 步加字符串时不用改任何函数签名。

## 5. 本步引入的核心概念

### 5.1 概念一：真值语义——为什么用数字表示布尔

**问题**：MiniLang 需要"真"和"假"这两个值（比如第 6 步的 `if` 条件）。但语言里只有数字（`double`）。布尔值从哪来？

**思路**：**不引入布尔类型。** 直接沿用 C 的真值规则：

| 表达式的值 | 真/假 | 在 MiniLang 里的表示 |
|---|---|---|
| `0` | 假 | `0` |
| `0.0` | 假 | `0` |
| `非 0`（`3`、`-0.5`、`0.001`） | 真 | `1` |

也就是说：**比较运算的结果一定是 `0` 或 `1`；`0` 假、非 `0` 真。**

**代码要点**：C 的 `==`、`<`、`>` 这些运算符本身就产出 `int` 类型的 `0` 或 `1`，所以实现起来只有一行：

```c
case T_LT: return number(a < b);
```

`number()` 是第 3 步定型的"造一个数字值"辅助函数。

**为什么这么设计（取舍）**：

- **好处 1**：C 里 `if (x)` 的条件本来就是"非 0 即真"，所以 MiniLang 的 `if` 直接用 C 的写法判断 `v.value != 0` 就行，第 6 步几乎不用写任何真值转换代码。
- **好处 2**：不用给词法分析器加 `true` / `false` 关键字。**这一点很重要**：词法分析器在第 1 步就定型了（INV-1），词法器再没改过。如果第 4 步临时起意想加 `true` / `false` 两个 token，就得回头改词法分析器、改 `type_name()`、改 `Token` 的 `text` 长度上限…… 全是连锁反应。
- **好处 3**：不引入新类型，就不用写类型检查逻辑。第 5 步定义变量时只需要检查"是不是字符串"，不用再检查"是不是布尔"。
- **代价**：MiniLang 里没法写 `let flag = true;`，只能写 `let flag = 1;`。同时 `1 && 2` 的结果是 `1` 而不是 `2`（C 的 `&&` 返回的是操作数本身）——见 5.3。

### 5.2 概念二：`!` 的实现

**问题**：`!x` 表示"取反"。`!0` 应该是 `1`，`!5` 应该是 `0`。

**思路**：根据 5.1 的真值规则，`x` 为假（`x == 0`）时 `!x` 为真（`1`），反之为假（`0`）。所以：

```
!x  ==  (x == 0)
```

**代码要点**（本步对 `eval` 的 `case N_UNARY:` 的改动）：

```c
case N_UNARY: {
    Value a = eval(n->a, e);
    if (n->op == T_MINUS) return number(-a.value);
    if (n->op == T_PLUS)  return number(a.value);
    /* ! 的真值规则：0 是假，非 0 是真 */
    return number(a.value == 0);
}
```

注意这里**没有 `if (n->op == T_NOT)`**，而是直接把 `!` 当成"兜底分支"。这是因为 `unary()`（第 2 步）只可能产生三种一元运算：`-`、`+`、`!`。前两个已经被 `return` 掉了，剩下的必然是 `!`。

**边界情况**：`!` 的优先级很高，比 `==` 还高。所以 `!0 == 1` 会被解析成 `(!0) == 1`，结果是 `1`：

```sh
$ ./minilang /tmp/not_eq.ml ast
语法树：
二元 EQ
├── 一元 NOT
│   └── 数字 0
└── 数字 1
求值结果：1
```

看树最直观：`<` 那一层挂的是 `一元 NOT`，不是 `数字 0`。如果 `!` 的优先级比 `==` 低，树就会长成另一副样子。

### 5.3 概念三：短路求值——本步最重要的 6 行

**问题**：`&&` 和 `||` 的语义是"两边都算"还是"只算够用的那几边"？

**思路**：**短路（short-circuit evaluation）**。这是几乎所有语言都有的规则：

| 表达式 | 求值策略 | 结果 |
|---|---|---|
| `a && b` | 先算 `a`；`a` 是假就**不** `b` | `a` 假 → `0`；否则看 `b` |
| `a \|\| b` | 先算 `a`；`a` 是真就**不算** `b` | `a` 真 → `1`；否则看 `b` |

**为什么必须短路**：因为右边可能有副作用或者会出错。最经典的例子：

```
0 && (1 / 0)
```

左边是 `0`（假），整个表达式的值必然是 `0`。如果实现成"两边都算"，右边 `1 / 0` 会触发"除数不能为 0"的致命错误——一个**本该短路成功的表达式却让程序崩溃了**。

**代码要点**：C 的 `&&` / `||` 是短路运算符，但**你不能直接把 C 的 `&&` 写在解释器的求值代码里**，因为 `eval()` 返回的是一个 `Value` **结构体**，C 不允许结构体参与 `&&`：

```c
/* 编译报错：invalid operands to binary expression ('Value' and 'Value') */
if (eval(n->a, e) && eval(n->b, e)) ...
```

而且更重要的是：**即使你能编译过，也不能这么做**。因为 C 的 `&&` 是"先算左边，看结果，再决定要不要算右边"——它短路的是**它自己的两个操作数**，而 `eval(n->a, e) && eval(n->b, e)` 里两个 `eval` 恰好就是两个操作数，看起来正好…… 但问题在于 `eval` 返回 `Value` 而不是 `int`，`Value` 又不能直接当布尔用（得写 `.value != 0`），一旦写成 `eval(n->a,e).value != 0 && eval(n->b,e).value != 0`，C 的短路就**只保证右边那个 `!= 0` 不算**，而 `eval(n->b,e)` 本身已经被算出来了——**求值顺序一改，短路就没了**。

所以，**短路必须手写**：在 `eval` 里，**先算左边，看左边，如果已经能确定结果，就直接 return，根本不去算右边**。

```c
case N_BINARY: {
    Value x = eval(n->a, e);

    /* 短路求值：&& 和 || 的右边可能根本不执行。
       0 && (1/0) 不应该报"除数为 0"，这就是短路的意义。 */
    if (n->op == T_AND && x.value == 0) return number(0);
    if (n->op == T_OR  && x.value != 0) return number(1);

    Value y = eval(n->b, e);   /* ← 只有走到这里，右边才会被求值 */
    ...
```

**这三行代码的位置极其关键**：它们必须在 `Value y = eval(n->b, e);` **之前**。放晚了，右边已经被算出来了，再判断也来不及。

**验证（真实运行）**：

```sh
$ ./minilang tests/case_03_short_circuit.ml ast
语法树：
二元 AND
├── 数字 0
└── 二元 SLASH
    ├── 数字 1
    └── 数字 0
求值结果：0
```

除零没有发生——右边根本没被执行。

**如果你写错了会怎样**：把上面那两行短路判断删掉（其余代码不变），重新编译再跑同一个用例：

```sh
$ cc -std=c11 -Wall -Wextra -O2 minilang.c -lm -o minilang_nosc
$ ./minilang_nosc tests/case_03_short_circuit.ml ast
错误 [1:9]: 除数不能为 0
语法树：
二元 AND
├── 数字 0
└── 二元 SLASH
    ├── 数字 1
    └── 数字 0
```

程序直接报错退出。**这就是"必须手写短路"的铁证。**

**另一半也要验证**：短路不是"永远不算右边"。`1 && (1 / 0)` 里左边是真，右边**必须**被算出来，于是报错：

```sh
$ ./minilang /tmp/and_true.ml ast
错误 [1:9]: 除数不能为 0
语法树：
二元 AND
├── 数字 1
└── 二元 SLASH
    ├── 数字 1
    └── 数字 0
```

这说明短路判断写对了：左边为真时老老实实去算右边。

**边界情况**：`||` 的短路方向相反。`0 || (1 / 0)` 里左边是假（不短路），右边必须被算，会报错：

```sh
$ ./minilang /tmp/or_false.ml ast
错误 [1:9]: 除数不能为 0
```

而 `1 || (1 / 0)` 里左边是真 → 直接短路返回 `1`，不报错。

### 5.4 概念四：比较运算返回 `0` / `1`

**问题**：`==` `!=` `<` `<=` `>` `>=` 这六个运算符的结果是什么类型？

**思路**：全部返回 `0`（假）或 `1`（真）。**注意是"真/假"，不是"操作数本身"**——这和 C 的 `&&` / `||` 不一样（C 的 `1 && 2` 结果是 `2`，因为 C 的 `&&` 产出的是操作数）。

```
        C 的 && / ||              MiniLang 的 && / ||
        ─────────────             ──────────────────
1 && 2  →  2 （右操作数）          1 && 2  →  1 （真）
0 || 5  →  5 （右操作数）          0 || 5  →  1 （真）
```

**代码要点**：

```c
/* 比较运算：结果只有 0（假）和 1（真） */
case T_EQ: return number(a == b);
case T_NE: return number(a != b);
case T_LT: return number(a <  b);
case T_LE: return number(a <= b);
case T_GT: return number(a >  b);
case T_GE: return number(a >= b);

/* 逻辑运算：两边都是真才算真 */
case T_AND: return number(a != 0 && b != 0);
case T_OR:  return number(a != 0 || b != 0);
```

**代码要点**：`a` 和 `b` 是 `double`，直接用 C 的比较运算符比较即可。`a == b` 在 C 里产出 `int` 的 `0` 或 `1`，`number()` 把它包成 `Value`。

**边界情况：浮点相等**。`3 == 3.0` 在 C 里是 `true`（`3.0` 和 `3.0` 的二进制表示相同），所以 MiniLang 里也是 `1`：

```sh
$ ./minilang /tmp/eq_float.ml ast
语法树：
二元 EQ
├── 数字 3
└── 数字 3
求值结果：1
```

但 `0.1 + 0.2 == 0.3` 是**假**（`0.1 + 0.2` 的浮点结果不等于 `0.3` 的精确值）。这是浮点数的固有性质，不是 MiniLang 的 bug。任何用浮点数做精确相等判断的语言都有这个问题。

### 5.5 概念五：语法一次建好，求值一步步加

**问题**：为什么本步的 diff 只有 `eval` 一个函数里的改动，一行语法分析器都没动？这正常吗？

**思路**：这正是**分步教学**的刻意设计。把一门小语言拆成 13 步，每一步只引入一个新概念，就得想办法让每一步的 diff 都足够小、足够聚焦。

**两种可能的排法**：

| 排法 | 第 4 步要做的事 | 问题 |
|---|---|---|
| **语法跟着语义一起加**（每步同时改词法、语法、求值） | 加 `==` 时要改词法（`T_EQ`）、改语法（`equal()` 那层）、改求值（`eval`） | 一步里塞三个层次，读者分不清"这个改动是词法的还是语法的还是求值的" |
| **语法一次建好，求值逐步加**（本教程的做法） | 加 `==` 时只改 `eval` | 前期步骤里有一堆"占位报错"，看着别扭 |

**我们选了第二种**，代价和收益都很明确：

- **代价 1**：第 3 步的 `eval` 里有一堆看起来很奇怪的代码：

  ```c
  case N_VAR:
      fatal_at(n->tok, "求值器还不支持变量，变量会在讲作用域时支持");
      break;

  case N_CALL:
      fatal_at(n->tok, "求值器还不支持函数调用，内置函数会在后面一步支持");
      break;
  ```

  这些"占位报错"是在告诉你：**这个语法我已经会解析了，只是还不会执行。** 提前把语法建好，是为了让后面的步骤专注于"执行语义"这一件事。

- **代价 2**：语法树打印器（`dump_ast`）里，第 3 步就已经能打印 `二元 LT` 这种节点了，但求值会报错。看起来"半成品"。

- **收益 1**：**每一步的 diff 都只碰一个层次。** 本步的 diff 只有 21 行新增、5 行删除，而且全部在 `eval` 里。你读这个 diff 的时候，脑子里只需要装"求值"这一件事。

- **收益 2**：**"解析得出来"和"执行得对"是两件可以分开验证的事。** 第 2 步验证了"`1 < 2` 能被解析成一棵树"，第 4 步验证了"这棵树能被算出 `1`"。中间隔了两步，读者能清楚地看到"语法早就有了，只是求值器后来才跟上"。

- **收益 3**：**词法分析器（INV-1）真的可以一次做全。** 如果第 4 步才加 `==`，那 `==` 这个 token 的识别、名字打印（`type_name`）、双字符运算符的处理逻辑都要在第 4 步加一遍，第 1 步"词法器一次做全"这条约定就不成立了。

**一个副产品**：本步的 `eval` 里，`case N_BINARY:` 的 `switch (n->op)` **删掉了 `default:` 分支**（第 3 步那里是 `default: fatal_at(n->tok, "比较与逻辑运算会在下一步支持");`）。删掉的理由是：现在六个比较运算符 + 两个逻辑运算符**全部有对应的 case**，没有任何一个 `op` 会落到"没有 case"的境地。

> ⚠️ 但这留下了一个隐患：**将来给 `N_BINARY` 加新运算符时，如果忘了加 case，`switch` 会静默地走到 `break;`，然后 `eval` 返回 `number(0)`——不报错，只是结果错。** 记住这一点（见第 8 节坑 4）。

### 6.2 分段讲解

#### 第 1 段：实现 `!`

```diff
         case N_UNARY: {

             if (n->op == T_MINUS) return number(-a.value);
             if (n->op == T_PLUS)  return number(a.value);

```

**逐行解释**：

- `Value a = eval(n->a, e);` 是第 3 步就有的：一元运算的子节点 `n->a` 本身是一棵表达式树，要先递归算出它的值。
- `if (n->op == T_MINUS) return number(-a.value);` 和 `if (n->op == T_PLUS) return number(a.value);` 也是第 3 步的代码，这里没动。
- **删掉的** `fatal_at(n->tok, "逻辑运算 ! 会在下一步支持"); break;` 是第 3 步埋下的**占位报错**。它的作用是：第 3 步还没有 `!` 的语义，如果用户写了 `!0`，就报一句人话提示"这一步还不支持"，而不是给出一个乱七八糟的值。
- **新加的** `return number(a.value == 0);`：`a.value == 0` 在 C 里是一个 `int` 类型的 `0` 或 `1`——`a.value` 是 `0` 时结果是 `1`（真），否则是 `0`（假）。`number()` 把它包成 `Value`，和 `case N_NUM:` 的返回值类型一致。

**为什么不用 `if (n->op == T_NOT)` 明确判断**：因为 `unary()`（第 2 步）只会产生 `-` / `+` / `!` 三种一元运算。前两个已经在上面 `return` 掉了，走到这一行必然是 `!`。这样写少一个分支，也少一次比较。

**如果你写错了会怎样**：

- 写成 `return number(a.value);` → `!0` 会得到 `0`（而不是 `1`），`!5` 会得到 `5`（而不是 `0`）。**完全反了**。验证：`./minilang tests/case_04_not.ml ast` 的期望输出是 `求值结果：1`，实际会得到 `0`，测试失败。
- 写成 `return number(a.value != 0);` → 同样反了。
- 忘了 `return`，只写 `number(a.value == 0);` → 编译报 `warning: statement with no effect`（`-Wall` 会报），而且函数会继续往下走到 `break;` 再返回 `number(0)`，结果恒为 `0`。
- 保留 `break;` 又加 `return` → 编译报 `unreachable code` 警告（不是错误，但很丑）。

#### 第 2 段：短路求值（关键！）

```diff
         case N_BINARY: {
             Value x = eval(n->a, e);
+
+            /* 短路求值：&& 和 || 的右边可能根本不执行。
+               0 && (1/0) 不应该报"除数为 0"，这就是短路的意义。 */
+            if (n->op == T_AND && x.value == 0) return number(0);
+            if (n->op == T_OR  && x.value != 0) return number(1);
+
             Value y = eval(n->b, e);
             double a = x.value, b = y.value;
             switch (n->op) {
```

**逐行解释**：

- `Value x = eval(n->a, e);` 是第 3 步的代码：**左边永远会被求值**。这是对的——`&&` 和 `||` 都需要先知道左边的值。
- **`if (n->op == T_AND && x.value == 0) return number(0);`** —— 这是 `&&` 的短路分支：
  - 条件成立意味着"运算符是 `&&`"**且**"左边是假（0）"。
  - 整个表达式的值必然是 `0`（假）。**右边完全不需要知道**。
  - 所以直接 `return`，`eval(n->b, e)` 那行永远走不到。
- **`if (n->op == T_OR && x.value != 0) return number(1);`** —— 这是 `||` 的短路分支：
  - 左边是真（非 0）时，整个表达式的值必然是 `1`（真），右边同样不需要算。
- **这两行必须在 `Value y = eval(n->b, e);` 之前**——这是本段最重要的一句话。一旦右边被求值了，再判断也来不及。

**为什么要手写而不能用 C 的 `&&`**：详细分析见 5.3。核心原因是 `eval` 返回 `Value` 结构体，C 不允许结构体参与 `&&`；就算改成 `eval(n->b,e).value != 0` 这种能编译的写法，求值顺序一变短路就失效了。

**如果你写错了会怎样**：

- **把这两行删掉**（最常见的错误）→ 编译能过，但 `tests/case_03_short_circuit.ml` 会失败，报 `错误 [1:9]: 除数不能为 0`。我在写这份 README 时真的编译过这个变体验证过。
- **把这两行放在 `Value y = eval(n->b, e);` 之后** → 同样报错除零。短路判断必须**前置**。
- **写成 `if (n->op == T_AND && x.value == 0) return number(x.value);`** → 结果凑巧是对的（`x.value` 就是 `0`），但语义是"返回左操作数"，和 MiniLang 的"返回 0/1"约定不一致。如果哪天左边的值不是严格的 `0`（比如 `0.0`），`x.value` 仍然是 `0`，还是对的。但更糟的情况是 `T_OR` 那行如果写成 `return number(x.value);`，`5 || 0` 会返回 `5` 而不是 `1`——**破坏了 5.4 节的约定**。所以统一写 `number(0)` / `number(1)`。
- **写成 `if (x.value == 0) return number(0);`（忘了判断 `n->op`）** → 这会让**所有**二元运算都短路！`1 + 0` 会直接返回 `0`，`5 - 3` 会返回 `0`。测试会大面积失败。
- **把 `T_AND` 和 `T_OR` 的条件写反** → `0 && 1` 会去算右边（还行），但 `1 || 0` 也会去算右边——如果右边是 `1/0` 就会错误地报错。

#### 第 3 段：比较运算与逻辑运算的真值

```diff

                     return number(fmod(a, b));   /* C 的 % 只支持整数，浮点取余要用 fmod */
-                default:
-                    fatal_at(n->tok, "比较与逻辑运算会在下一步支持");

+                case T_NE: return number(a != b);
+                case T_LT: return number(a <  b);
+                case T_LE: return number(a <= b);
+                case T_GT: return number(a >  b);
+                case T_GE: return number(a >= b);
+
+                /* 逻辑运算：两边都是真才算真 */
+                case T_AND: return number(a != 0 && b != 0);
+                case T_OR:  return number(a != 0 || b != 0);
             }
             break;
         }
```

**逐行解释**：

- **删掉的** `default:` 和那句占位报错。删 `default` 之后，`switch (n->op)` 里必须**穷举所有** `N_BINARY` 可能出现的运算符，否则会掉到 `break;` 然后返回 `number(0)`（静默错误）。
- `a` 和 `b` 是 `double`（上一段里 `double a = x.value, b = y.value;` 定义的）。C 的 `==`、`!=`、`<`、`<=`、`>`、`>=` 对 `double` 全部合法，结果是 `int` 的 `0` 或 `1`。
- `case T_AND: return number(a != 0 && b != 0);` —— 这一行**只有在第 2 段的短路没触发时才执行到这里**，也就是说 `a` 和 `b` 都已经被算出来了。所以这里的 `&&` 是 C 的普通 `&&`，作用只是"两个布尔值相与"。
- `case T_OR: return number(a != 0 || b != 0);` 同理。
- 注意 `case T_AND` 的结果和 C 不同：C 的 `1 && 2` 是 `2`，这里 `1 && 2` 是 `1`。见 5.4。

**如果你写错了会怎样**：

- **写成 `case T_AND: return number(a && b);`** → 编译能过（`double` 在 C 里可以当条件用，0 假非 0 真），结果也**恰好**是对的（`a && b` 在 C 里产出 `0` 或 `1`）。但它依赖"C 允许 double 当条件"这个隐式约定，不如显式写 `a != 0 && b != 0` 清楚。
- **写成 `case T_LT: return number(a < b ? 1 : 0);`** → 结果一样，但多此一举。
- **忘记给某个运算符加 case**（比如漏了 `T_GE`）→ `>=` 会掉到 `break;`，`eval` 返回 `number(0)`，**不报任何错**。这是本步最容易犯、也最难发现的错误。补救办法见第 8 节坑 4。
- **把 `case T_LE` 写成 `case T_LTE`** → 编译报 `use of undeclared identifier 'T_LTE'`。

## 8. 易错点与坑

### 坑 1：把短路判断写在 `eval(n->b, e)` 之后

- **错误现象**：`0 && (1 / 0)` 仍然报 `错误 [1:9]: 除数不能为 0`。
- **原因**：短路判断的**位置**比它的**内容**更重要。`Value y = eval(n->b, e);` 这一行一旦执行，右边就真的被算了。判断写在它后面，只是"算完之后再看一眼"，毫无意义。
- **正确写法**：判断必须夹在 `eval(n->a, e)` 和 `eval(n->b, e)` 之间。

### 坑 2：想用 C 的 `&&` 来实现短路

- **错误现象**：`invalid operands to binary expression ('Value' and 'Value')` —— 编译直接失败。
- **原因**：`eval()` 返回的是 `Value` **结构体**，C 不允许结构体参与 `&&` / `||`。
- **正确写法**：手写两行前置判断。**不要试图把 `eval` 改成返回 `int`**——那样会破坏整个 `Value` 抽象（`is_string`、`string` 字段就白留了），而且要改动所有调用点。

### 坑 3：短路判断忘了判断运算符

- **错误现象**：`1 + 0` 的求值结果变成了 `0`；`5 - 3` 变成了 `0`。
- **原因**：写成 `if (x.value == 0) return number(0);` —— 这会让**所有**二元运算都在左边为 0 时短路返回 0。`+`、`-`、`*`、`/` 全被误伤。
- **正确写法**：`if (n->op == T_AND && x.value == 0) ...`，两个条件都要写。

### 坑 4：`switch` 里漏了 case，程序**不报错**但结果错

- **错误现象**：你给 `N_BINARY` 加了新运算符（比如第 7 步的 `++`），忘了加对应的 `case`。程序不崩溃，只是那个运算的结果恒为 `0`。
- **原因**：本步**删掉了 `default:` 分支**（第 3 步那里有）。删掉 `default` 之后，`switch` 遇到没匹配上的 `op` 会静默走到 `break;`，然后 `eval` 返回 `number(0)`。
- **正确写法**：两个习惯——(1) 加新运算符时，`case` 必须和运算符一一对应；(2) 养成"改完 `switch` 就跑一遍全部用例"的习惯，因为这类错误**只有测试能发现**，编译器不会提醒你。
- **补救办法**：如果想更安全，可以把 `default` 加回来，指向一个明确的报错：

  ```c
  default:
      fatal_at(n->tok, "未实现的二元运算符");
  ```

  本教程选择不加，理由见第 10 节。

### 坑 5：`!` 的优先级比你想的高

- **错误现象**：你以为 `!x == 0` 是 `!(x == 0)`，实际是 `(!x) == 0`。
- **原因**：`unary()` 在优先级链里比 `equal()` 高得多。`!` 先结合。
- **正确写法**：想表达 `!(x == 0)` 要写 `!(x == 0)`（加括号）。养成"拿不准就加括号"的习惯。

### 坑 6：以为 `&&` 的结果和 C 一样

- **错误现象**：写 `1 && 2` 期望得到 `2`（C 的语义），实际得到 `1`。
- **原因**：C 的 `&&` 产出的是**操作数**，MiniLang 的 `&&` 产出的是**真/假**（见 5.4）。这是刻意设计的：MiniLang 里没有布尔类型，只有"0 假非 0 真"，统一成 0/1 更一致。
- **正确写法**：想要操作数本身就显式写：`1 && 2` → 你要的其实是 `2` 的话，写成 `(1 != 0 && 2 != 0) ? 2 : 0`，或者干脆换个写法。实践中这个差异几乎不会咬人。

### 坑 7：`a == b` 里 `a`、`b` 是 `double`，别指望它精确

- **错误现象**：`0.1 + 0.2 == 0.3` 得到 `0`（假）。
- **原因**：浮点数的二进制表示问题，跟 MiniLang 无关。
- **正确写法**：比较浮点相等时留一个容差，比如 `a - b < 1e-9`。本教程的用例里都是整数比较，碰不到这个坑。

**Q4.** `1 && 2` 在 MiniLang 里得到 `1`，在 C 里得到 `2`。为什么不一样？哪个更"对"？

**Q5.** 本步的 `switch (n->op)` 里为什么删掉了 `default:` 分支？删掉之后有什么风险？

<details>
<summary>参考答案</summary>

**A1.** 因为词法分析器在第 1 步就定型了（INV-1），之后再没改过。加入 `true` / `false` 关键字意味着要改：`lex()` 里的关键字识别表、`type_name()` 里的名字映射、`Token` 结构体的 `text` 长度上限（`MAX_TEXT`）可能也要重新掂量。而且会让"第 1 步词法器一次做全"这条约定站不住脚。不引入布尔类型的收益是：所有真值判断都退化成"非 0 即真"，和 C 完全一致，第 6 步的 `if` 几乎不用写转换代码。

**A2.** `!` 是取反：`x` 是假（`x == 0`）时 `!x` 是真（`1`）。所以 `!x` 的值就是 `x == 0` 这个表达式的值。写成 `!= 0` 会把语义反过来（变成"x 是真"），`!0` 会得到 `0`、`!5` 会得到 `1`，全反。

**A3.** 两个原因：(1) `eval` 返回 `Value` 结构体，C 不允许结构体参与 `&&`，编译都过不了；(2) 更本质的是，`&&` 要短路就必须"在决定要不要算右边之前就知道左边的值"，这要求把求值拆成"先算左边 → 判断 → 再决定算不算右边"三步，而 C 的 `&&` 只能作用于**已经被求值完毕的两个操作数**。你想用 `eval(n->a,e).value != 0 && eval(n->b,e).value != 0` 蒙混过关时，C 短路掉的是右边那个 `!= 0` 比较，而 `eval(n->b, e)` 本身作为 `&&` 的另一个操作数**已经被求值了**——顺序一变，短路就没了。

**A4.** C 的 `&&` 产出操作数本身（`1 && 2` → `2`），MiniLang 的 `&&` 产出真/假（`1 && 2` → `1`）。哪个"对"取决于语言设计。MiniLang 选择 0/1 是因为它只有 `double` 一种类型，没有布尔类型；如果 `&&` 允许返回任意操作数，那"0 假非 0 真"的规则就变得模糊（`1 && 2` 得到 `2`，那 `2` 是真还是……？还是真，但 `&&` 的结果就不再是布尔了）。统一成 0/1 让"条件的值"永远只有两种形态，C 的 `if (x)` 判断逻辑可以原样复用。

**A5.** 因为现在六个比较运算符 + 两个逻辑运算符全部有对应的 `case`，没有任何 `op` 会落空，保留 `default` 只会让编译器在 `-Wswitch` 下报"这个 case 永远走不到"之类的噪音（虽然 `n->op` 是 `int` 不是枚举，通常不会报）。风险是：**将来加新运算符时忘了加 `case`，`switch` 会静默走到 `break;`，`eval` 返回 `number(0)`，不报任何错**。这种错误只有测试能发现。

</details>

### 9.2 预测题（"改一行会发生什么"）

**Q6.** 把 `if (n->op == T_AND && x.value == 0) return number(0);` 改成 `if (n->op == T_AND && x.value == 0) return number(x.value);`，`tests/case_03_short_circuit.ml` 的输出会变吗？

**Q7.** 把这两行短路判断整体**下移**到 `Value y = eval(n->b, e);` 之后，`tests/case_03_short_circuit.ml` 的输出会变吗？

**Q8.** 把 `case T_AND: return number(a != 0 && b != 0);` 改成 `case T_AND: return number(a && b);`，输出会变吗？

**Q9.** 把 `case T_LT: return number(a < b);` 改成 `case T_LT: return number(a <= b);`，`tests/case_01_less_than.ml` 的输出会变吗？**用哪个用例能抓出这个 bug？**

<details>
<summary>参考答案</summary>

**A6.** 不变（`求值结果：0`）。因为短路分支里 `x.value` 本来就等于 `0`（短路条件就是 `x.value == 0`），`number(x.value)` 和 `number(0)` 完全等价。但这是**巧合**：这个写法把"返回布尔"变成了"返回左操作数"，破坏了 5.4 节的约定。把它套到 `T_OR` 那行就露馅了：`if (n->op == T_OR && x.value != 0) return number(x.value);` 会让 `5 || 0` 返回 `5` 而不是 `1`。

**A7.** **会变，而且测试会失败。** 下移之后，右边 `1 / 0` 先被求值，直接触发 `fatal_at(n->tok, "除数不能为 0")`，程序以退出码 1 结束。stderr 变成 `错误 [1:9]: 除数不能为 0`。这正是坑 1 说的"位置比内容更重要"。

**A8.** 不变。`a` 和 `b` 都是 `double`，C 允许 `double` 直接当条件用（`0` 假、非 `0` 真），`a && b` 产出的就是 `int` 的 `0` 或 `1`，和 `a != 0 && b != 0` 结果完全一致。这两种写法在 C 里等价。区别只是可读性——显式写 `!= 0` 更清楚地表明"我们依赖的是 C 的真值规则"。

**A9.** `tests/case_01_less_than.ml` 的输出**不变**（`1 < 2` 和 `1 <= 2` 都是真，都得到 `1`）。**抓不出这个 bug！** 能抓出来的是 `1 <= 2` 和 `2 <= 2` 这类边界——但本步的测试用例里恰好没有这种输入。这说明了一件事：**测试用例的覆盖面决定了你能抓出多少 bug**。你可以自己写一个 `2 <= 2`（改成 `<` 会得到 `0`）和 `1 <= 2`（改成 `<` 会得到 `1`，看不出差别）来验证。

</details>

### 9.3 动手题（改代码 + 跑 tests 验证）

**Q10.** 在 `004/` 下新建一个 `my_cases/` 目录，写四个 `.ml` 文件，用 `./minilang` 跑出真实输出并记录：

- `t1.ml`：`5 > 3` → 期望 `求值结果：1`
- `t2.ml`：`5 == 5.0` → 期望 `求值结果：1`（浮点相等）
- `t3.ml`：`1 || (1 / 0)` → 期望 `求值结果：1`，**不报错**
- `t4.ml`：`0 && (1 / 0)` → 期望 `求值结果：0`，**不报错**

**Q11.** 把 `004/minilang.c` 复制成 `/tmp/nosc/minilang.c`，删掉那两行短路判断，编译后跑 `t3.ml` 和 `t4.ml`，记录真实输出和退出码。然后解释：为什么 `t3.ml` 在**没有**短路的情况下也不会报错？

**Q12.**（进阶）给 MiniLang 加一个"三目逻辑运算"的支持是做不到的（因为没有布尔类型），但你可以试试给 `N_BINARY` 加一个新运算符（比如 `T_MOD`——虽然 `T_PERCENT` 已经占了 `%` 的位置）。请回答：如果加一个 `case T_XXX:` 但**忘了**在 `default` 被删除的情况下写全所有 case，会发生什么？用 `tests/case_01_less_than.ml` 和一个自造的 `1 < 2 == 1` 之类的表达式验证你的猜想。

<details>
<summary>参考答案</summary>

**A10.** 四份 `.ml` 的真实运行结果：

```
$ ./minilang my_cases/t1.ml ast
语法树：
二元 GT
├── 数字 5
└── 数字 3
求值结果：1

$ ./minilang my_cases/t2.ml ast
语法树：
二元 EQ
├── 数字 5
└── 数字 5
求值结果：1

$ ./minilang my_cases/t3.ml ast
语法树：
二元 OR
├── 数字 1
└── 二元 SLASH
    ├── 数字 1
    └── 数字 0
求值结果：1

$ ./minilang my_cases/t4.ml ast

二元 AND
├── 数字 0
└── 二元 SLASH
    ├── 数字 1
    └── 数字 0
求值结果：0
```

`t3.ml` 和 `t4.ml` 的 stderr 都是空的，退出码都是 0。

**A11.** 删掉短路判断后：

- `t4.ml`（`0 && (1/0)`）→ stderr 变成 `错误 [1:9]: 除数不能为 0`，退出码 1。
- `t3.ml`（`1 || (1/0)`）→ **仍然不报错**，输出 `求值结果：1`，退出码 0。

为什么？因为 `||` 的短路方向是"左边为真就跳过右边"，而 `1` 恰恰**就是真**。没有短路实现时，`1 || (1/0)` 的流程是：算左边 `1` → 算右边 `1/0` → **报除零**。

等等——那为什么它没报错？让我把代码重新看一遍…… 没有短路判断时，代码会无条件执行 `Value y = eval(n->b, e);`，右边 `1/0` 一定会被算出来，一定会报错。

**修正后的答案**：`t3.ml` 在**没有**短路的情况下**也会报错**（`错误 [1:9]: 除数不能为 0`）。`||` 的短路只有在实现里显式写了 `if (n->op == T_OR && x.value != 0) return number(1);` 这行时才存在。删掉短路判断，`||` 和 `&&` 一样都会无条件计算右边。

（这一点值得反复强调：**短路不是"语言自带的语义"，而是你在 `eval` 里手写的一段控制流。** 没有那两行，C 的 `||` 和 `&&` 在 MiniLang 里就只是普通的二元运算符。）

**A12.** 忘写 case 的后果是：`switch (n->op)` 找不到匹配的 case，直接落到 `break;`，然后 `eval` 走到函数末尾的 `return number(0);`。所以那个运算的结果**恒为 0**，而且**不报任何错**，退出码还是 0。

验证思路：写一个 `1 < 2 == 1` 之类的表达式——注意 `==` 的优先级**低于** `<`（优先级链是 `equal` → `compare`），所以它被解析成 `(1 < 2) == 1`，即 `二元 EQ` 的左边是 `二元 LT`。如果把 `case T_EQ` 的实现改坏（比如写成 `number(a != b)`），这个表达式的结果就会从 `1` 变成 `0`，而程序不会报任何错。**这就是"静默错误"的可怕之处**：只有对照期望输出才能发现。

</details>

## 10. 本步的设计取舍

**为什么本步只改 `eval` 一个函数？**

因为第 2 步建立语法分析器时，我们**故意把整条优先级链一次建全**（`logical_or → logical_and → equal → compare → add → mul → unary → primary`）。这样做的代价是：第 3 步（算术求值）里有一堆"占位报错"（"比较与逻辑运算会在下一步支持"、"逻辑运算 ! 会在下一步支持"），看起来像半成品。收益是：从第 3 步开始，每一步都只需要动**一个层次**——第 3 步只动算术求值，第 4 步只动比较与逻辑求值，第 5 步才动语句层。读者的注意力可以完全集中在当步的新概念上。

**为什么不引入独立的布尔类型？**

见 5.1。核心理由是 INV-1：词法分析器一次做全，中途加 `true`/`false` 会打破这条约定。其次是 MiniLang 的定位——一门只有数字的小语言，"0 假非 0 真"是最简单的规则，且和 C 完全一致。

**为什么不把 `&&` 的结果做成"操作数本身"（像 C 那样）？**

因为 MiniLang 里没有布尔类型。如果 `1 && 2` 得到 `2`，那"条件的值"就有无穷多种形态，读者得记住"`0` 是假，别的都是真"之外还要记住"`&&`/`||` 产出的是操作数"。统一成 0/1 之后，第 6 步的 `if (x)` 只要写 `v.value != 0` 就行，不用管 `x` 是从哪儿来的。

**代价：不能写 `let flag = true;`。**

用户想要布尔变量只能写 `let flag = 1;`。在实际使用中这 hardly（几乎不）是个问题，因为 MiniLang 目前只有 `if` 会消费布尔值，而 `if` 直接吃表达式。

**还没做的：**

- 没有短路之外的条件求值优化（解释器不在乎）。
- 没有位运算（`&` `|` `^` `<<` `>>`）和 `&` `|` 形式的短路运算符。
- 没有三元运算符 `?:`（虽然 C 代码里用了三目，但那是实现细节，不是 MiniLang 的语法）。
- 没有"逻辑与/或"返回操作数的变体（像 Python 的 `and`/`or` 那样）。
- `switch` 里删掉了 `default`，加新运算符时容易静默出错（见坑 4）。

## 11. 下一步预告

到目前为止，MiniLang 只会**算一个表达式**——它还不能"做一件事"。下一节我们迈出最关键的一步：把 MiniLang 从"表达式求值器"变成"真正的解释器"。

你会看到**语句（statement）和表达式（expression）的区别**：`1 + 2` 求出一个值，而 `let x = 1;` 只是"做一件事"（定义一个变量）。我们会引入 `let`、赋值、代码块 `{ }`，以及最核心的**作用域链（scope chain）**——一层套一层的环境，查找变量时从内往外找，内层遮蔽外层。你会亲手把 `Env` 从一个空壳变成真正能存变量的结构，并且理解为什么 `Env` 的变量表必须是**动态数组**而不是固定长度的 `Var vars[2048]`——那个选择牵涉到 `sizeof(Env)` 是 24 字节还是 272 KB，在递归时是"能跑"和"段错误"的差别。
