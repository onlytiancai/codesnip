## 3. 现在的程序能做什么

第 1 步就有错误处理函数，但那时候报出来的信息只有一行：

```
错误 [1:9]: 未定义变量 'price'
```

用户看到"第 1 行第 9 列"，得自己数格子才知道是哪一列。

本步加上了**源码行 + 指示符**：

```
错误 [1:9]: 未定义变量 'price'
   1 | let x = price + 1;
     |         ^
```

**注意第一行一个字都没变**——格式还是 `错误 [行:列]: 说明`。
新信息是**追加**在后面的两行。所以第 1~11 步的行为**一个字节都没变**，
之前写的测试用例全部照样通过。

| 能力 | 状态 |
|---|---|
| 报错误的类型、行列号、原因 | 第 1 步就有 |
| 附带出错的那一行源码 | **本步新增** |
| `^` 指示符精确指向出错的字符 | **本步新增** |

## 4. 前置知识回顾

第 1 步定型的两个错误函数（INV-7），到今天**一个字都没改过**：

```c
static void error_at(int line, int col, const char *fmt, ...) {
    va_list ap;
    fprintf(stderr, "错误 [%d:%d]: ", line, col);
    va_start(ap, fmt); vfprintf(stderr, fmt, ap); va_end(ap);
    fputc('\n', stderr);
    had_error = 1;
}

static _Noreturn void fatal_at(Token t, const char *fmt, ...) {
    va_list ap;
    fprintf(stderr, "错误 [%d:%d]: ", t.line, t.col);
    va_start(ap, fmt); vfprintf(stderr, fmt, ap); va_end(ap);
    fputc('\n', stderr);
    had_error = 1;
    exit(1);
}
```

区别只有一个：

| | `error_at` | `fatal_at` |
|---|---|---|
| 参数 | `(line, col, fmt, ...)` | `(Token, fmt, ...)` |
| 之后 | **继续执行** | `exit(1)` 结束程序 |
| 用在哪 | 目前**没有**调用点 | 几乎所有地方 |

`error_at` 存在的意义是"将来做错误恢复（收集多个错误）时用得上"，
但教学版目前没有用到它——所以 `had_error` 这个标志其实也没起什么作用。

## 5. 本步引入的核心概念

### 5.1 概念一：为什么要显示源码行

设想两种报错：

```text
错误 [3:13]: 未定义变量 'price'
```

```text
错误 [3:13]: 未定义变量 'price'
   3 | let z = x + price;
     |             ^
```

第二种多花了两行，但用户**不用再打开源文件数格子**。
对于"第 137 行第 42 列"这种位置，差别是决定性的。

### 5.2 概念二：`print_source_line` 怎么找到那一行

源码在全局变量 `src` 里（一个以 `'\0'` 结尾的大字符串），
所以不用再传一遍：

```c
static void print_source_line(int line, int col) {
    if (!src || line <= 0) return;

    /* 找到第 line 行开头的位置 */
    const char *p = src;
    int cur = 1;
    while (cur < line && *p) {
        if (*p == '\n') cur++;
        p++;
    }
    if (cur != line) return;      /* 这一行不存在（比如行号是 0） */

    const char *end = strchr(p, '\n');
    size_t len = end ? (size_t)(end - p) : strlen(p);
    ...
}
```

**逐行解释**：

- `if (!src || line <= 0) return;` —— 两个防护：
  `src` 可能还没读进来（理论上不会，但 `env_push` 里有个 `line = 0` 的假 token），
  `line <= 0` 表示"这个错误没有位置信息"，这时候不该打印源码行。
- 从头开始扫，**每遇到一个 `'\n'` 就把行号加一**，
  扫到第 `line` 行就停。
- `if (cur != line) return;` —— 文件可能没那么多行（比如错误行号是 0，
  或者源码被截断），这时候不打印，免得打印出**错误的那一行**。
- `strchr(p, '\n')` 找这一行的结尾。**如果找不到（最后一行没有换行符）**，
  退化成 `strlen(p)`——这是 `end ? ... : ...` 的作用。

### 5.3 概念三：指示符怎么对齐（这里有个容易错一格的地方）

```c
fprintf(stderr, "%4d | ", line);
...
fprintf(stderr, "     | %*s^\n", caret, "");
```

**逐列数**：

```text
   3 | let z = x + price;
     |             ^
^^^^^   ← 源码行前缀：4 列数字 + " | " = 7 列
     |             ^
^^^^^   ← 指示符前缀：5 个空格 + "| " = 7 列
```

两个前缀**必须一样长**，否则 `^` 会比它指的那个字符偏左或偏右一格。

源码行用 `"%4d | "`（4 列数字 + 空格 + 竖线 + 空格 = 7 列），
指示符行没有行号，要用 **5 个空格** + `"| "` 补齐这 7 列。

**如果你写错了会怎样**：指示符前缀写成 4 个空格（6 列），
`^` 就会**整体偏左一格**——看起来"差不多"，但仔细一对就发现指错了位置。
这类 bug 很难靠肉眼发现，所以本步的测试用例把期望输出**逐字节**固定住了。

### 5.4 概念四：`caret` 是怎么算出来的

```c
int caret = col - 1 - start + (start > 0 ? 3 : 0);
fprintf(stderr, "     | %*s^\n", caret, "");
```

- `col` 是**从 1 开始**的列号，而 `%*s` 的宽度是"要打印几个空格"，
  所以要 `col - 1` 转成"从 0 开始的下标"。
- `- start` 是因为超长行被截断时，窗口不是从第 0 列开始的，
  要减去窗口起点的偏移。
- `+ (start > 0 ? 3 : 0)` 是补偿窗口前面那个 `...` 占的 3 列。

`%*s` 这个技巧值得记住：**用宽度参数打印空格**，
比手写一个循环或者 `printf("%*s", n, "")` 更省事，也不用准备一个空格字符串。

### 5.5 概念五：超长行要截断

```c
#define MAX_SHOW_COLS 160     /* 出错时一行最多显示多少列源码 */
```

```c
/* 太长的行只截取出错位置附近的一段，免得一行刷出几万个字符 */
int start = 0;
if (len > MAX_SHOW_COLS) {
    start = col - 1 - MAX_SHOW_COLS / 2;
    if (start < 0) start = 0;
    if (start > (int)len - MAX_SHOW_COLS) start = (int)len - MAX_SHOW_COLS;
}
int show = (int)len - start;
if (show > MAX_SHOW_COLS) show = MAX_SHOW_COLS;

fprintf(stderr, "%4d | ", line);
if (start > 0) fputs("...", stderr);
fprintf(stderr, "%.*s", show, p + start);
if (start + show < (int)len) fputs("...", stderr);
fputc('\n', stderr);
```

**问题**：源码里有一行 50000 个字符（机器生成的文件很容易这样），
出错时把整行打出来，终端直接被刷爆。

**思路**：以出错位置为中心，截取最多 160 列，前后用 `...` 标记。

**逐行解释**：

- `start = col - 1 - MAX_SHOW_COLS / 2;` —— 让窗口**以出错位置为中心**。
  再做两次边界修正：`start < 0` 说明出错位置太靠前，窗口要左移；
  `start > len - MAX_SHOW_COLS` 说明太靠后，窗口要右移。
- `fprintf(stderr, "%.*s", show, p + start);` ——
  **`%.*s` 的 `*` 表示"精度从参数里取"**。这里用它来打印**恰好 `show` 个字符**，
  不用先 `strncpy` 到临时缓冲区。
  （`%*s` 是宽度从参数取，`%.*s` 是精度从参数取——两个 `*` 各管一件事。）
- `if (start > 0) fputs("...", stderr);` —— 前面被切掉了才加前缀；
  `if (start + show < (int)len)` —— 后面被切掉了才加后缀。

**如果你写错了会怎样**：忘了 `if (start > 0)` 的判断，
那么短行也会被加上 `...`，看起来像被截断过——虽然不影响正确性，但很迷惑。

### 5.7 概念七：遇到第一个错误就停

教学版策略：**第一个错误就 `exit(1)`**，不做错误恢复。

**优点**：

- 实现简单（`fatal_at` 直接退出，不需要错误对象、不需要回溯、不需要清理栈上的资源）。
- 不会因为第一个错误引发一连串莫名其妙的连锁错误。

**缺点**：

- 用户一次只能看一个错误，改完再跑才知道下一个。
- 语法错误尤其吃亏：第一个错可能让后面的源码根本没被解析。

**更好的做法**（真实编译器都这么做）：

1. 错误不立即退出，而是**记到一个列表里**（`Error { Token tok; char *msg; }`）。
2. 语法分析器在**能恢复的地方**继续（跳过一条语句、跳过到 `;` 或 `}`）。
3. 全部解析完再把错误列表打印出来。
4. 运行期错误仍然立即停（因为后面的执行结果已经没有意义了）。

MiniLang 的语法分析器是**递归下降**的，恢复起来比带 LR 文法表的做法难，
所以教学版没做——这是一个明确的取舍，不是遗漏。

### 6.2 分段讲解

#### 6.2.1 定位并打印那一行

```c
/* 找到第 line 行开头的位置 */
const char *p = src;
int cur = 1;
while (cur < line && *p) {
    if (*p == '\n') cur++;
    p++;
}
if (cur != line) return;      /* 这一行不存在（比如行号是 0） */
```

**逐行解释**：

- `cur` 是"当前扫到第几行"，从 1 开始（和 token 里记的 `line` 一致）。
- 循环的**条件**里有 `&& *p` —— 扫到文件末尾就停。
  少了这个检查，源码最后一行没有换行符时会一直读越界。
- 循环体里**先判断再前进**：只有当前字符是 `'\n'` 才加行号，
  然后 `p++` 跳过这个换行符。所以循环结束时 `p` 正好指向第 `line` 行的开头。
- `if (cur != line) return;` —— 如果扫到文件末尾了还没到第 `line` 行，
  说明这个行号不存在（比如源码被截断，或者 `env_push` 传的 `line = 0`）。
  这时候**宁可不打印**，也不要打印错误的行。

#### 6.2.2 取出一行的内容

```c
const char *end = strchr(p, '\n');
size_t len = end ? (size_t)(end - p) : strlen(p);
```

**逐行解释**：

- `strchr(p, '\n')` 找这一行的换行符。
- `end ? (end - p) : strlen(p)` —— **指针相减得到的是元素个数**，
  这正是这一行的长度（不含换行符）。如果 `end` 是 `NULL`（最后一行没有换行符），
  就退回到"从这里到文件末尾"的长度。

**如果你写错了会怎样**：写成 `end - p` 而不判断 `end`，
最后一行没有换行符时 `end` 是 `NULL`，`NULL - p` 是**未定义行为**，
`len` 变成一个巨大的数，`fprintf("%.*s", show, p + start)` 会打印出海量垃圾
（或者直接崩）。

#### 6.2.3 对齐指示符

```c
fprintf(stderr, "%4d | ", line);
...
fprintf(stderr, "     | %*s^\n", caret, "");
```

**逐行解释**：

- `"%4d | "` —— 行号右对齐在 4 列里（超过 4 位就撑开），
  然后是 `" | "`。总前缀 **7 列**。
- `"     | "` —— 5 个空格（代替行号的 4 列 + 1 个分隔空格）+ `"| "`。
  总前缀**也是 7 列**，两行才能对齐。
- `%*s` 的 `*` 从参数 `caret` 取宽度，打印 `caret` 个空格，然后打 `^`。

- `print_source_line` 放在 `fputc('\n', stderr)` **之后**——

## 8. 易错点与坑

### 坑 1：指示符前缀少一列

**现象**：`^` 比它指的字符**偏左一格**。

**原因**：源码行前缀 `"%4d | "` 是 7 列，指示符行写成 `"    | "` 只有 6 列。

**正确写法**：指示符行用 `"     | "`（5 个空格 + `"| "`），同样是 7 列。

这类 bug 靠肉眼极难发现——**所以要靠测试用例把期望输出逐字节固定住**。

### 坑 2：忘了判断 `end` 是 `NULL`

**现象**：源码最后一行没有换行符时，程序打印出一大堆乱码或者崩溃。

**原因**：`end - p` 在 `end == NULL` 时是未定义行为。

**正确写法**：`size_t len = end ? (size_t)(end - p) : strlen(p);`

### 坑 3：`%.*s` 的精度和 `strlen` 混用

**现象**：打印的行末尾多出一些字符。

**原因**：`%.*s` 的精度是"最多打印多少个字符"，但如果字符串更短，
它就只打印到 `'\0'`——**不会**越界。但如果误以为它一定会打印 `show` 个字符，
就会算错列数。

**正确写法**：算 `caret` 时用的偏移要和实际打印的窗口一致。

### 坑 4：往 stdout 打印错误信息

**现象**：程序输出和错误信息混在一起，重定向时看不清。

**原因**：错误信息写到了 `stdout`。

**正确写法**：所有错误信息都用 `fprintf(stderr, ...)`。
本教程的测试用例也是**分别比对 stdout 和 stderr** 的。

### 坑 5：`print_source_line` 里用了 `cur` 这个名字

**现象**：和 `cur()` 函数重名，虽然不冲突（一个是变量一个是函数），
但读代码时会绕。

**正确写法**：局部变量换个名字，比如 `cur_line`。

### 坑 6：以为 `error_at` 会在出错后继续跑

**现象**：写了 `error_at(...)` 之后代码继续执行，访问了一个还没定义的变量。

**原因**：`error_at` 只是打印，**不会阻止后续执行**。
目前 `error_at` 没有任何调用点，所以这个坑还没被踩到。

**正确写法**：需要"打印后立刻停下"时用 `fatal_at`。

## 9. 自测题

### 9.1 概念题

**Q1.** `error_at` 和 `fatal_at` 有什么区别？为什么两个都要有？

<details><summary>参考答案</summary>

`error_at` 打印后**继续执行**，`fatal_at` 打印后 `exit(1)`。
`fatal_at` 多一个 `_Noreturn` 标记，告诉编译器"这个函数不会返回"，
所以它后面的代码不可达——这让编译器能给出更准确的警告，
也省掉了在调用点写 `return` 的麻烦。
两个都要留，是为了将来做错误恢复（收集多个错误）时用 `error_at`。

</details>

**Q2.** 为什么第一行错误信息的格式**没有改**？

<details><summary>参考答案</summary>

因为改了就会破坏前面 11 步的所有行为和测试用例。
新信息是**追加**在后面的，所以是纯粹的增强。
这体现了"先定格式、后加内容"的开发方式。

</details>

**Q3.** `print_source_line` 里为什么要 `if (cur != line) return;` 这一句？

<details><summary>参考答案</summary>

防止打印出**错误的行**。比如源码只有 3 行，错误行号却是 5（理论上不该发生），
或者 `env_push` 传的假 token `line = 0`。这时候宁可什么都不打印，
也不能打印一行不相干的源码来误导用户。

</details>

### 9.2 预测题（改一行会发生什么）

**Q4.** 把指示符前缀 `"     | "` 改成 `"    | "`（少一个空格），输出会变成什么样？

<details><summary>参考答案</summary>

`^` 整体**偏左一格**。比如 case_02 本来指向 `price` 的 `p`（第 13 列），
改后会指向第 12 列（`+` 后面那个空格）。
`case_02` 会挂——因为期望输出是逐字节比对的。

</details>

**Q5.** 把 `print_source_line` 里的 `if (start > 0) fputs("...", stderr);` 删掉，
短行（不超过 160 列）会输出成什么样？

<details><summary>参考答案</summary>

短行不受影响（`start == 0`，本来就不加前缀）。
但超长行的**前面**会少一个 `...`，而且 `caret` 的计算里 `+ 3` 的补偿还在，
所以 `^` 会偏右 3 列。
`case_01`~`case_06` 全是短行，所以这六个用例**都测不出来**——
这正好说明"测试用例要覆盖边界情况"。

</details>

**Q6.** 把 `print_source_line(line, col);` 从 `fatal_at` 里删掉，
`case_02` 的期望输出要改哪一部分？

<details><summary>参考答案</summary>

要删掉最后两行（源码行和指示符），只保留第一行：
```
错误 [3:13]: 未定义变量 'price'
```
其他五个用例也一样。

</details>

### 9.3 动手题

**Q7.** 把 `MAX_SHOW_COLS` 从 160 改成 40，然后造一个长行触发错误，
看看截断效果。

```sh
cd 012
sed -i '' 's/#define MAX_SHOW_COLS 160/#define MAX_SHOW_COLS 40/' minilang.c
python3 -c "print('let x = ' + '1+'*50 + 'undefined_var;')" > /tmp/long.ml
./minilang /tmp/long.ml
```

<details><summary>参考答案</summary>

会打印出错位置附近的 40 列，前后带 `...`，`^` 仍然准确指向 `undefined_var` 的 `u`。
把 `MAX_SHOW_COLS` 改回 160。

</details>

**Q8.** 给 `error_at` 找一个用武之地：让"变量数量超出上限"这个错误
用 `error_at` 而不是 `fatal_at` 打印，然后观察程序的行为。

<details><summary>参考答案</summary>

`env_push` 里现在是：
```c
if (e->count >= MAX_VARS)
    fatal_at((Token){.line = 0, .col = 0}, "变量数量超出上限");
```
改成 `error_at(0, 0, ...)` 之后，程序**不会停下来**，
而是继续往数组里写——因为 `env_push` 没有 `return`，
紧接着的 `snprintf` 就会写到 `e->vars[MAX_VARS]` 之外，**越界**。

这说明 `error_at` 不是"随便换个函数名"就行——
**调用点必须自己决定要不要继续**。这正是"错误恢复"难做的地方。

</details>

**Q9.** 把 `case_06_missing_semicolon.ml` 的内容改成 `let x = 10`（**不带结尾换行**），
重新跑一遍，看看报错有什么不同。

<details><summary>参考答案</summary>

错误信息一样，但源码行会显示成 `   2 | `（第 2 行是空行）——
因为文件末尾的换行符让第 2 行存在（虽然是空的）。
如果文件真的没有末尾换行，`strchr` 找不到 `'\n'`，
`len` 会退化成 `strlen(p)`，第 2 行就不存在，`print_source_line` 直接返回，
输出里只有第一行错误信息。

</details>

### 9.4 延伸题

**Q10.** 如果要让解释器一次报出**多个**错误，最小的改动是什么？

<details><summary>参考答案</summary>

把 `fatal_at` 里的 `exit(1)` 去掉，改成"记到错误列表里然后返回"。
但这样 `fatal_at` 就不能是 `_Noreturn` 了，所有调用点的控制流都要改
（`fatal_at(...)` 之后代码还会继续执行）。
更麻烦的是**语法恢复**：解析器报完错要跳到下一个能继续的位置
（比如跳过到 `;` 或 `}`），否则解析状态会乱掉。
所以"多错误报告"听起来简单，实际上是编译器里最麻烦的一块。

</details>

## 10. 本步的设计取舍

- **只改两行既有代码**：诊断信息是"附加"的，不改变已有行为。
  这让前面 11 步的测试用例一个都不用改。
- **超长行截断**：多写 15 行代码，换来"机器生成的文件不会刷屏终端"。
  这是个典型的"教学版会省、实际项目不能省"的细节。
- **不实现错误恢复**：教学版选了最简单可靠的策略。
  真实编译器（clang、gcc）都会收集多个错误——但那需要语法恢复机制，
  和这套递归下降解析器不搭。
- **`error_at` 目前没有调用点**：它是为了将来准备的。
  留着一个没人用的函数有点怪，但正好体现了"先把接口定下来"的做法。
