# 020.py — 大矩阵乘法的「增量算子」优化

## 一、为什么会有这个题目

### 1.1 真实世界里反复出现的场景

很多算法并不是一次算出最终矩阵乘，而是在迭代地修改其中某个因子。下面这些场景都会遇到「矩阵乘法中途增量扩列 / 扩行」：

| 场景 | 谁被扩展 | 触发条件 |
|---|---|---|
| 注意力机制的 KV cache | K、V 各追加 1 列 | 自回归解码每生成一个新 token |
| 在线学习 / FMRI | 嵌入表追加新行 | 冷启动用户、新观测进入 |
| RAG 检索索引 | 词向量矩阵追加新行 | 新文档入库 |
| LoRA 合并 | 权重矩阵追加 Δ 列数 | 增大 rank |
| 求解线性方程组增量更新 | 系数矩阵补一行 | 新约束到达 |

如果按 `O(n^3)` 整块重算，每次新数据进来都要把整张矩阵乘一遍；这一次性浪费常常是系统吞吐的瓶颈。能不能只算「多出来的那部分」，把「已经算过的」留下来——这就是「增量算子」的核心动机。

### 1.2 题目本身的精炼描述

> 给定两个大矩阵 $A$、$B$，先算 $C = A \cdot B$ 并把 $C$ 缓存在 GPU 上；之后 $A$ 在行方向追加 $\Delta A$、$B$ 在列方向追加 $\Delta B$，得到 $A'$、$B'$。需要重新计算 $C' = A' \cdot B'$。
>
> 问：能不能利用已缓存的 $C$，只算「新增的几块」？
>
> 答：能 —— 用分块矩阵恒等式直接展开即可。

## 二、数学原理

### 2.1 分块矩阵展开

设 $A \in \mathbb{R}^{m \times k}$，$B \in \mathbb{R}^{k \times n}$，「扩展」定义为：

$$
A' = \begin{pmatrix} A \\ \Delta A \end{pmatrix} \in \mathbb{R}^{(m+\Delta m)\times k},
\qquad
B' = \begin{pmatrix} B & \Delta B \end{pmatrix} \in \mathbb{R}^{k\times(n+\Delta n)}.
$$

按矩阵乘法把 $A'$、$B'$ 的四个块两两配对，得到：

$$
A'B' \;=\; \begin{pmatrix} A \\ \Delta A \end{pmatrix}\begin{pmatrix} B & \Delta B \end{pmatrix}
\;=\;
\begin{pmatrix}
\boxed{AB} & A\Delta B \\
\Delta A \, B & \Delta A\,\Delta B
\end{pmatrix}.
\tag{1}
$$

(1) 式的左上角 $AB$ **就是**已经算好且缓存在显存里的 $C$。把这一块直接 `out[:m, :n] = C` 就拿到结果了；剩下三块都是较小的、独立的矩阵乘，可以交给同一个 GPU 流水并行执行。

### 2.2 FLOPs 对比

把总计算量写出来（一次乘加算 2 FLOPs）：

| 方法 | 计算量 | 备注 |
|---|---:|---|
| naive：$A'B'$ 整块算 | $2(m+\Delta m)(n+\Delta n)k$ | 全部从头算 |
| incremental：左上 $\Delta$ + 三块新 | $\underbrace{0}_{\text{复用缓存}}+2mk\Delta n + 2\Delta m\,k\,n + 2\Delta m\,k\,\Delta n$ | 仅算新增 |

节省比例：

$$
\text{saved} = \frac{mn}{(m+\Delta m)(n+\Delta n)}.
\tag{2}
$$

例如 $m=n=k=4096$，$\Delta m=\Delta n=512$，代入 (2)：

$$
\text{saved}=\frac{4096^2}{4608^2}\approx 0.79\;(\text{约 }79\%).
$$

这就解释了为什么 dm、dn 越小相对收益越大 —— 越能摊薄「必须重算」的新增三块。

### 2.3 为什么还能更快（不只是省 FLOPs）

FLOPs 节省只是故事的一半；实际运行时还有几条加成：

1. **更小的子矩阵进 L2 cache**：每个子矩阵的 footprint 通常比完整乘积小一个数量级，命中率高。
2. **并行自由度更高**：三块新矩阵乘彼此独立，GPU 调度器把它们排到不同 SM 上可获得真并行（naive 单一巨型 GEMM 受单个核 tile 限制）。
3. **左上的 memcpy 是 DMA-like 搬移**：在 GPU 上等同于一次 `cudaMemcpyAsync`，带宽高、计算量几乎为 0。

实测加速比通常比 (2) 给出的「纯 FLOPs 比例」还要稍差一些，因为分配/调度/launch 等常数项还是得付。这就引出了下面要谈的「加速比-理论比」 gap 的取舍。

## 三、PyTorch 里怎么实现

### 3.1 直接复用 `addmm`

PyTorch 没有内建「带形状推断的 GEMM that 把结果写到任意张量切片」，但 `torch.addmm` 一行搞定：

```python
torch.addmm(input, mat1, mat2, beta=0, alpha=1, out=dest_slice)
# 等价于 dest_slice = mat1 @ mat2, 但不分配中间张量
```

把 (1) 式写成代码：

```python
out = torch.empty((m + dm, n + dn))
out[:m,   :n] = C_cached                    # 复用缓存
torch.addmm(torch.zeros(m,  dn),  A,  dB, 0,1, out=out[:m,  n:])   # 右上
torch.addmm(torch.zeros(dm, n ),  dA, B,   0,1, out=out[m:,  :n])   # 左下
torch.addmm(torch.zeros(dm, dn),  dA, dB,  0,1, out=out[m:,  n:])   # 右下
```

### 3.2 设备与同步原语

脚本里做了一个三层回退：

```python
def pick_device():
    if   torch.cuda.is_available():                   return torch.device("cuda")
    elif torch.backends.mps.is_available():           return torch.device("mps")
    else:                                             return torch.device("cpu")

def sync(device):
    if   device.type == "cuda": torch.cuda.synchronize()
    elif device.type == "mps":  torch.mps.synchronize()
```

`torch.mps.synchronize()` 是 PyTorch 2.0+ 才有的；老版本会 fallback 到 CPU，但本机是 2.12，没问题。

### 3.3 中位数 + warm-up

GPU 第一次跑 kernel 时要编译并 cache，后续每次计时都做 `torch.mps.synchronize()` 把区间卡紧；warm-up 三次后再测：

```python
def bench(device, fn, iters=10):
    for _ in range(3):    fn()           # warm-up
    sync(device)
    s = []
    for _ in range(iters):
        sync(device)
        t0 = time.perf_counter()
        fn()
        sync(device)
        s.append((time.perf_counter() - t0) * 1000)
    s.sort()
    return s[len(s)//2]                  # 取中位数
```

中位数比均值抗抖动好——单次 kernel launch 的尾延迟在大矩阵上对均值有 1–3 ms 的污染。

### 4.3 怎么读这张表

- **加速比 > FLOPs 比 × k**：在 dm=128 这种「极小扩展」下，FLOPs 节省 94%，实测拿到 9.82×，说明除 FLOPs 之外 kernel launch 和 cache locality 也贡献明显。
- **加速比 < FLOPs 比**：在 dm=2048 时，FLOPs 节省 44% 但只拿到 1.71×。当三块新矩阵和左上块大小接近时，多个小 GEMM 的 launch overhead 摊不上 FLOPs 收益，加速比就开始打折。
- **趋势**：随着 $\Delta m, \Delta n$ 增大，左上块在 $A'B'$ 里占比降低，能省的越来越少。极限 $\Delta m, \Delta n \to \infty$ 时加速比 → 1（缓存的相对贡献消失）。

## 五、几个工程提醒

1. **缓存必须就地复用**：拓展前后 $A$, $B$ 的内容不能变；否则左上角就不是当初的 $C$。
2. **正确性零误差是常态**：(1) 是恒等式，没有任何数值近似；和 Strassen / cuBLAS 不同实现造成 `1e-6` 的差别对比，这套是 bit-exact。
3. **设备自适应**：脚本自动适配 CUDA / MPS / CPU。换成 NVIDIA 后台测试要重新装 torch 的 CUDA wheel，别直接 copy 通用版本。
4. **dtype 影响**：实测是 fp32。torch 2.x 下 `torch.set_float32_matmul_precision("high")` 会用 TF32 跑 GEMM，naive 的绝对速度会明显变快，但加速比的走势不会改变。
5. **更大的扩展**：当 $\Delta m, \Delta n \gg m, n$ 时，分块矩阵法并不会让结果更便宜——只能在「扩展远小于原始规模」时享受缓存收益。

## 六、能扩展的方向

- **多向扩展**：分块切得更细，比如 $A'$、$B'$ 各分 $N$ 块，验证 $N\times N$ 增量复用的可组合性。
- **dtype 对照**：fp32 / TF32 / bf16 三档精度下分别跑，看加速比稳定性。
- **跨设备复用**：把缓存落到 CPU pinned memory 或 CUDA Unified Memory，演示跨设备增量复用。
- **嵌入到 KV cache**：把 incremental matmul 接到自回归推理里，看单 token 的 prefill/decode 阶段收益对比。
- **误差累积**：在 N 次连续扩展（每次生成 1 行 1 列）下观察累积误差；理论上仍是 0，串行跑可以验证。

## 七、参考

- **分块矩阵乘法** 在数值线性代数里是最基本的技巧，参见 Golub & Van Loan《Matrix Computations》第 1 章。
- **Woodbury 恒等式** $(A+UCV)^{-1}=A^{-1}-A^{-1}U(C^{-1}+VA^{-1}U)^{-1}VA^{-1}$ 是另一种「在已算矩阵上做低秩增量」的经典恒等式，可作为后续延伸。
- **torch.addmm** 的 `out=` 参数在 PyTorch 官方文档里作为「GEMM + 写回任意张量」的最佳实践出现。
