# 临时库测试指南（后端手测 / 冒烟）

> 这份文档记录的是**不碰真实库**地测后端接口的办法 —— 一套临时 env + 临时 SQLite +
> 后台跑一个临时 server，然后用 curl 打接口。
>
> 起因：套餐/配额/管理员、邮箱验证码这些功能都要建表、改用户数据，直接拿
> `server/data/app.db` 测会把真实库搞脏（多出测试用户、测试邮箱、被踢掉的会话）。
>
> 写给「改了后端要验证一下，但不想动真实数据」的时候看。

---

## 1. 为什么要临时库

| 直接测真实库 | 临时库 |
|---|---|
| 库里多出一堆 `mailtest` / `testuser` 之类的垃圾账号 | 测完 `rm -rf` 一下就没了 |
| 禁用/改套餐/重置密码会改到**真实用户**的会话 | 只影响临时库里的影子数据 |
| 验证码、发信记录会堆进真实 `email_codes` 表 | 用完即弃 |
| 出问题不好回滚（库是 gitignore 的，改了就是改了） | 删目录 = 恢复出厂设置 |

代价：要另起一个 server 实例（另一个端口），并且**凭据要自己带**（见下一节）。

---

## 2. 搭临时环境

### 2.1 写一个临时 env 文件

`SERVER_ENV_FILE` 指向的文件会**整体替换** `server/.env`（见 `server/src/config/env.ts`：
`.env` 优先于 shell 环境变量，想临时换配置只能用这个变量）。

```
# /tmp/mail-test/test.env
PORT=8797                      # 别跟真服务器（8787）撞端口
DB_PATH=/tmp/mail-test/test.db # 临时库 —— 绝对路径
AUTH_LOCAL_BYPASS=0            # 关掉「本地工具免登录」，强制走真实鉴权
DEBUG=1                        # 打 [auth] / [mail] / [usage] 日志
ADMIN_USERNAME=admin
ADMIN_PASSWORD=admin123       # 临时库里的账号，随便设
```

> ⚠️ 这个文件里**不要写真实凭据** —— 它只是给临时库用的。
> 真正要用的 key（比如 Resend 的 `RESEND_API_KEY`）在启动时用 shell 从真 `.env` 里取，
> 见 2.2。

### 2.2 启动临时 server

```bash
cd server
RESEND_API_KEY="$(grep '^RESEND_API_KEY=' .env | cut -d= -f2-)" \
SERVER_ENV_FILE=/tmp/mail-test/test.env \
pnpm exec tsx src/index.ts > /tmp/mail-test/server.log 2>&1
```

（Bash 工具里用 `run_in_background` 跑，输出重定向到日志文件。）

**为什么 key 要用 `$(...)` 现取**，而不是写进临时 env 文件：

- Claude Code 的安全分类器会拦「把带凭据的文件复制到 /tmp」「把 key 写进临时文件」这类操作
- `$(grep ... .env | cut ...)` 是**当场从真 .env 里读**，不落地成第二个副本，
  分类器也认得这是「用已授权的 key 跑一次测试」
- 分类器如果还是拦，就说明这一步需要用户明确授权，别绕

启动后确认一下：

```bash
head -5 /tmp/mail-test/server.log   # 应该看到 [db] /tmp/mail-test/test.db 和 listening on 8797
```

### 2.3 用 cookie jar 保持登录态

curl 的 `-c` 存 cookie、`-b` 带 cookie：

```bash
curl -s -c /tmp/mail-test/c1.txt -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"admin123"}' \
  http://127.0.0.1:8797/api/auth/login
```

## 3. 读临时库看数据

SQLite 用 Node 内置的 `node:sqlite`（Node 22+ 需要 `--experimental-sqlite`）：

```bash
cd server
node --experimental-sqlite -e "
const {DatabaseSync}=require('node:sqlite');
const db=new DatabaseSync('/tmp/mail-test/test.db');
console.log(JSON.stringify(db.prepare('SELECT email,code,attempts FROM email_codes ORDER BY id DESC LIMIT 1').get()))
" 2>&1 | head -3
```

**看验证码就是这么干的** —— 验证码是明文存库里的，不用去翻邮箱。

> ⚠️ SQL 里字符串字面量要用**单引号**（`'mailtest'`），双引号在 SQLite 里是「标识符」，
> 会报 `no such column: "table"`。
>
> ⚠️ 只查自己造的那几行（比如 `WHERE username='mailtest'`），别把整张 users 表打出来 ——
> 里面是真实用户的邮箱。

## 4. 收尾

```bash
# 1. 停掉临时 server（后台任务用 TaskStop）
# 2. 删临时目录
rm -rf /tmp/mail-test
```

`rm` 单独一次调用，别和别的命令串在一起。

## 5. 按功能分类的手测清单

### 5.1 鉴权 / 邮箱验证码

```bash
BASE=http://127.0.0.1:8797

# 发注册码（邮箱不能已注册）
curl -s -H 'Content-Type: application/json' -d '{"email":"xxx@qq.com"}' $BASE/api/auth/register/code
# 带码注册
curl -s -H 'Content-Type: application/json' \
  -d '{"username":"testuser","email":"xxx@qq.com","password":"test1234","code":"123456"}' \
  $BASE/api/auth/register
# 用邮箱登录 / 用用户名登录
curl -s -H 'Content-Type: application/json' -d '{"username":"xxx@qq.com","password":"test1234"}' $BASE/api/auth/login
# 发重置码 + 重置密码
curl -s -H 'Content-Type: application/json' -d '{"email":"xxx@qq.com"}' $BASE/api/auth/password-reset/code
curl -s -H 'Content-Type: application/json' \
  -d '{"email":"xxx@qq.com","code":"123456","newPassword":"newpass9"}' $BASE/api/auth/password-reset
```

要覆盖的分支：码错 / 码过期 / 码用过 / 60 秒冷却 / 试错上限 / 重置后旧 session 失效。

### 5.2 套餐 / 配额 / 管理员

- 注册 → 默认免费版；`/api/auth/me` 看 `plan` 和 `quota`
- 灌用量把配额撑爆 → 消耗 token 的接口 403「配额已用完」
- 管理员改套餐 / 禁用 / 启用 / 审核升级申请 / 生成邀请码 → 每条都跑一遍
- **非管理员调 `/api/admin/*` 必须 403**

## 6. 踩过的坑（都是真的卡过的）

### 6.1 两次「发验证码」之间隔了 60 秒 → 冷却测不出来

冷却逻辑是「同一邮箱 60 秒内不能重复发」。但**两次 Bash 调用之间可能隔好几分钟**
（工具调用本身有延迟，分类器超时更久），于是第二次请求时冷却早就过期，
返回 200，看起来像「冷却没生效」。

**正确做法：一条命令里连发两个请求。**

```bash
curl -s -w ' <- %{http_code}\n' -H 'Content-Type: application/json' \
  -d '{"email":"xxx@qq.com"}' http://127.0.0.1:8797/api/auth/password-reset/code \
  --next -s -w ' <- %{http_code}\n' -H 'Content-Type: application/json' \
  -d '{"email":"xxx@qq.com"}' http://127.0.0.1:8797/api/auth/password-reset/code
```

期望：第一个 `200`，第二个 `429`。

> 踩过的坑：以为 `-d ... -d ...` 会发两个请求 —— 不会，**body 会被拼在一起**，
> 服务端直接报 `SyntaxError: Unexpected non-whitespace character after JSON`。
> 必须用 `--next` 分隔。

### 6.2 `node -e` 混用 `require` 和顶层 `await`

```bash
node -e "const {DatabaseSync}=require('node:sqlite'); ... await fetch(...)"
# → SyntaxError: await is only valid in async functions
```

要么全用 `require` + `.then()`，要么加 `--input-type=module` 并改成 `import`。

### 6.3 分类器会拦「复制 .env」「写 key 到临时文件」

- `cp server/.env /tmp/xxx/test.env` → 被拦（凭据泄漏）
- `Write` 一个含真实 key 的临时文件 → 被拦

绕法（本项目认可的做法）：**不复制**，用 `$(grep ...)` 从真 `.env` 现取。

### 6.4 发信失败时，验证码会「白等冷却」

码是先落库再发信的。发信失败如果不删掉这行，用户就得等 60 秒冷却才能重试。
**发信失败要 `deleteEmailCode(id)`**（`routes/auth.ts` 的 `sendCode` 里已经这么做了）。

### 6.5 SQL 漏了一列 → 接口返回 null（不是报错！）

`findSessionUser()` 少写了 `u.email`，结果 `/api/auth/me` 安静地返回 `email: null` ——
**没有任何报错**，只是前端显示「未绑定邮箱」。

教训：给 `User` 这类对象加字段后，把**所有**构造它的地方都过一遍：
`USER_COLUMNS` / `authenticate()` / `findSessionUser()` / `listUsers()` —— 每个 SQL
都有各自的 SELECT 列表，漏一个就是一个静默的 null。

### 6.6 `tsx watch` 会自动热重载

你本地跑的是 `pnpm dev`（`tsx watch`）的话，**改完代码真实服务器立刻就是新的**，
不用重启 —— 但也意味着你改着改着，真实库就被新代码动了（所以才需要临时库那一套）。

### 6.7 跑完一定要收尾

后台 server 进程 + `/tmp` 里的临时库 + cookie jar，都要清掉。
否则端口占着（下次起 server 报 EADDRINUSE），临时库还在（下次测的时候是旧数据）。

---

## 7. 最后的三道关

改完代码（不管测没测）都要跑一遍：

```bash
cd server && pnpm type-check && pnpm test    # 后端：tsc + vitest（现有测试必须全绿）
cd .. && pnpm build                          # 前端：vue-tsc + vite build
```

**不要新增自动化测试**（项目约定）—— 新功能靠这套手测 + 调试日志验证。
